# Enrich contacts

Collection results may use `delivery: "file"`. In that case, `preview` and `metadata` are compact and may be shortened; download `file.downloadUrl` and process the complete JSON in code before selecting or importing rows. If the download is blocked, as in Claude Cowork, read the same result with `trayo_read_result { resultId }` and follow `page.nextCursor` while `page.hasMore` is true; this never repeats the search. Keep the original `hasMore`/`nextCursor` pagination, and do not repeat the search to get its file. Use `output: "file"` when a download is wanted, or `output: "pages"` when you cannot download files.

1. `trayo_whoami` once. Read `lookups.email.remaining` or `lookups.phone.remaining` for the requested field's plan allowance snapshot; do not calculate it from `limit` and `used`. `null` means no plan lookup cap for that field, but workspace quota, the rolling 24-hour daily usage limit (`quota_daily_limit`), and request checks can still refuse work. Describe a numeric value as remaining plan allowance, not a promise that those lookups will start or find contact details. Stop if `canInitiate` is false (workspace lifecycle) or the field's capability is unavailable; explain its `blockedBy` reasons. An available capability does not guarantee acceptance. Handle the actual refusal code and `stoppedBy.retry` as described in step 6.
2. Get the people into the workspace first. A lookup takes Trayo person ids and nothing else: the `id` on a find row belongs to the search, not to your workspace, and means nothing here.
   - Already there: `trayo_list_people`, filtered by `accountId`, `q` (a substring of the name), `updatedSince`, or `hasEmail: "false"` to leave out everyone who already has one. The boolean filters take the literal string `"true"` / `"false"`. Page with `nextCursor` until `hasMore` is false; `data[].id` is the id you want.
   - Not there yet: `trayo_add_people`, up to 200 rows of `{ fullName, title, linkedinUrl, accountId | company }`. `fullName` is the only required field, and the professional profile URL is the upsert key inside an account, so send it whenever you have it. Read ids from both `created` and `updated`; an `updated` row matched an existing person by LinkedIn or email and wrote the fields you sent. A `skipped` row with `reasonCode: "duplicate"` is a name-only match left unchanged, so use its `existingId` only after confirming it is the same human. `reasonCode: "identity_conflict"` means LinkedIn and email identify different people; send one identity, or PATCH the intended record. Every created or updated receipt also carries `fullName`: when the user picked people by name, take the id from the receipt with that name (one over 28 characters comes back cut, ending in `…`), never by counting positions in the rows you sent, because every lookup spent on the wrong person is spent for good. Then read `degraded`, which names rows that DID land but landed incomplete: `no_account` is a row with no account, `no_identity` a row with neither a LinkedIn nor an email — that one has no deduplication key, so running this again creates it a second time. Say so rather than reporting a clean import.
3. Keep the complete set of workspace person ids selected for enrichment, deduplicated by id, including ids from both `created` and `updated`, plus duplicate `existingId` receipts you confirmed are the same human. Split it into batches of at most 200; unless an allowance stops the run (step 6), submit every batch, including the final partial batch (238 people means 200 plus 38). Track outcomes by person id and requested field across calls; a response covers only the ids submitted in that call. Start the lookups: `trayo_enrich_emails { personIds, waitSeconds }` — up to 200 ids, `waitSeconds` 0–45 (default 30). Send only the people the user will actually use: every lookup that starts draws on the workspace's email allowance, and the allowance is the thing you cannot get back. A person whose address is already known, already being looked up, or in the cooldown after a miss is reported per person in `accepted[].skipped` with the reason (`manual_present`, `already_found`, `in_progress`, `retry_too_soon` with `retryAvailableAt`, `start_failed`) and costs nothing, so re-sending the same people is safe and never looks twice.
4. Read what landed in `contacts` — the picture at the END of the wait, which is newer than `accepted[].contact` (the state when the lookups started). Per person: `email.value` is what to use, `email.source` says `manual` (someone wrote it) or `enrichment`, and `email.status` is `verified`, `bounced` (the value is withheld) or `stale`. `verified` means a finder returned the address as a hit — it is not an acceptance probe, and not a claim that it belongs to the person: `email.identityConfidence` answers that (`match` when the local-part agrees with their name or the domain with their account's website, `conflict` when either disagrees — a catch-all or a wrong-account hit, `unknown` when there is nothing to compare, null when unscored). Do not send to a `conflict` without a human look, and say so in the output. `email.lookup.state` is `in_progress` while it runs, then `found` or `not_found`. A `not_found` is an answer — Trayo did not find an address for that person — not a failure to retry. The top-level `skipped` is the ids this call could not act on at all — unknown or another workspace's, a duplicate earlier in the batch, or people the allowance or time budget never reached (step 6).
5. Anything still running comes back in `next`, naming the exact `trayo_get_contacts { personIds }` call that reads it. Use that tool to poll, and no faster than the wait it offers: it is free — it starts no lookup and spends no allowance — and it returns as soon as nothing is running.
6. The allowance can end a call. `stoppedBy { reason, retry, field, notLookedUp }` on an otherwise successful answer means it ran out part-way: those people are in `skipped`. Branch on `retry` and `reason` rather than on the prose in `next`. Each `reason` has its own remedy: `"lookup_limit_reached"` is the plan's own lookup allowance, so the plan has to change; `"quota_exceeded"` is the workspace's own quota, so raise it or wait for it to renew at the next billing cycle; `"quota_daily_limit"` clears on its own as usage ages out of the rolling 24-hour window. Say which one it is and stop for now, do not loop. When the allowance refuses before anything starts, the whole call is one of those three errors instead, carrying the same recovery guidance (`do_not_retry` for the first two, `retry_later` for the daily limit).
   A time stop is different from an allowance stop: `next` and `skipped[].reason` say the call ran out of time. Re-submit only those time-skipped `personId` values in smaller batches, within the user's original selection. Do not retry every top-level `skipped` row: duplicates need no new lookup, invalid ids need correction, and an allowance refusal follows the remedies above. Poll people already running instead of submitting them again. If a retry makes no progress, stop and report the unresolved ids and reason rather than looping.
7. Phone numbers only when the user asks for them: `trayo_enrich_phones`, same arguments, same waiting, same reading. It is a separate tool because it draws on a separate allowance and needs a separate scope (`people:enrich_phone`), so a key allowed to find addresses may still be refused numbers, and neither tool can spend the other's allowance. `trayo_get_contacts` polls both at once.

Never guess an address from a name and a domain, and never write a guess into a record: the point of this job is that the value is sourced. `email.value` stays null until a lookup finds one or someone writes one.

## Finish

Hand back a table of name, title, company, `email.value`, `email.status` and `email.identityConfidence` — a `contacts` row carries `personId`, `email` and `phone` and no name, so join it to the people you listed or added by that id. Flag every `conflict` row, and say plainly how many people have no address yet and why (still running, not found, or never looked up).

Before reporting completion, reconcile the full selected id set against all batch outcomes, separately for each requested field. Every selected person must have a current result, an explicit refusal/skip, or be listed as still running or not yet submitted. Submit any accidentally omitted ids while the request remains authorized and no allowance stop blocks them. Read the latest contact state for running lookups before counting results; if they are still running, report them as pending, never as not found or failed. Report totals for the whole selection, counting each person once per field, and preserve unresolved ids with their reasons for resuming later.

By now you must have: reconciled every selected id, including the final partial batch; told the user how many lookups remained (`limit - used` from `trayo_whoami`) before starting any; sent only the people they will use; stopped, not looped, when the allowance ended a call.

Offer these in one line, then wait for the user's pick:
- Keep it in Trayo: `trayo_add_to_list` `{ name, members: [{ personId, via }] }` — `via` is provenance a human will read later, so set it honestly (`find` for people a search produced, `manual` otherwise).
- Re-run it on your cadence: recipe `stakeholders-at-a-company` (people who become records) or `contact-without-importing` (someone who need not) at `https://api.trayo.ai/v1/recipes`; for people already in the workspace, `POST /v1/people/enrich/batch` then `GET /v1/people/{id}/enrich` — retain each request's `personIds` array and map `skipped[].index` back to it. Re-send only rows whose reason says the call ran out of time, in smaller batches; allowance refusals require the remedy above, and invalid ids or duplicates must not enter a blind retry loop. The 45-second budget is checked between people, so a lookup already being started can extend the response beyond it.
- Hand it off: a CSV written from the rows you hold.
